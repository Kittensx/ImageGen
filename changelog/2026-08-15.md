# ImageGen Update — 2026-08-15

> **Status:** Alpha development snapshot

## Advanced Models Step 0

IMAGE_GEN now has an initial component-native model composition path alongside the existing whole-checkpoint workflow.

### Free-form component composition

A new **Use Advanced Models** control switches generation from the normal checkpoint selector to registry-backed component selection. The user selects a model family and then chooses the learned components for that composition independently.

The initial family contracts cover SD 1.x, SD 2.x, SDXL, and SD3/SD3.5 roles already represented by the component registry.

### Required Auto behavior

Required component roles support Auto only when exactly one unique compatible component fingerprint is available. If the registry contains multiple unique compatible fingerprints, IMAGE_GEN requires an explicit user choice instead of guessing.

Registry occurrences are deduplicated by component fingerprint, so multiple physical copies of the same component appear as one logical choice with multiple source locations.

### Optional roles remain opt-in

Optional components are not silently enabled. They use **Off** as the default and require an explicit component selection.

For SD3/SD3.5, T5/T5XXL remains optional. Whole-checkpoint SD3 behavior continues to use the qualified CLIP-L + CLIP-G path unless the user explicitly enables a T5 component through Advanced Models.

### T5 execution placement

An explicitly selected T5/T5XXL component now has a separate execution-device policy:

* CPU preserves the qualified low-VRAM CPU conditioning path;
* CUDA is available as an explicit choice for higher-VRAM GPUs; and
* Auto uses CUDA only when the resolved memory policy is high-VRAM, otherwise CPU.

### Whole checkpoints remain supported

Turning Advanced Models off preserves the existing `.safetensors` checkpoint and VAE-selection path. Turning Advanced Models on disables and ignores those whole-model selectors for generation, including startup checkpoint preloading from a saved Advanced Models session.

### Residency and replay safety

Resident model reuse now includes the advanced composition fingerprint so two compositions sharing the same denoiser donor cannot accidentally reuse different VAE or text-encoder state. Advanced component selections are also retained through replay, batch, queue-composer, and output-manifest surfaces.

## Component-Native Models Phase 01 - Contracts and Registry Data Model

The component-native model work now has explicit cross-family contracts instead of relying on SD3-era and Step 0 role tables as the architectural authority.

### Architecture family providers

SD 1.x, SD 2.x, SDXL, and SD3/SD3.5 now have provider contracts defining their canonical family identity, required and optional component roles, base-weight role, structural constraints, digital-hydration capability, placement capability, and blueprint/reconstruction capability state.

Step 0 Advanced Models role definitions are derived from these providers. The old `FAMILY_ROLE_SPECS` export remains only as a compatibility view for existing callers.

### Durable component identity and source records

The asset registry now adds normalized `component_identities` and `component_sources` records while retaining existing `asset_components` snapshots as source evidence.

Opening an existing registry backfills the normalized records from already-stored component hashes and metadata. The migration does not read or rehash model payload bytes merely because the schema changed.

The registry also reserves additive tables for later blueprint, saved-composition, component-policy, compatibility-validation, and materialized-metric phases without activating those later behaviors early.

### Stable service boundary

A `ComponentRegistryService` now exposes provider contracts, discovered-family state, component candidates, selection resolution, Auto-resolution explanations, component source explanations, registry health, existing targeted/registered refresh behavior, and future blueprint/composition record reads without requiring UI code to query SQLite directly.

### Phase validation

`test_validations\component_native_phase01_validation.bat` runs the focused code gate and gathers real-library evidence into:

`data\validations\component_native_models\phase01\component_native_phase01_validation_bundle.zip`

The evidence pass uses real configured checkpoint/VAE/text-encoder roots and header-only model inspection. It reports unregistered files, ambiguous or unsupported architectures, stale component-role caches, normalized source forms, family coverage, and unknowns that should shape Phase 02 rather than being guessed in code.

### Evidence state is separate from implementation state

Family providers now report runtime/digital-hydration validation state separately from whether the code path exists. SD3 carries forward its qualified production evidence while T5 CUDA remains explicitly hardware-evidence pending. SD 1.x, SD 2.x, and SDXL component-composition paths are represented by providers but remain marked as requiring real-model validation rather than being declared proven from code structure alone.
