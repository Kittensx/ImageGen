# ImageGen Update — 2026-08-18

> **Status:** Alpha development snapshot

This source update expands ImageGen's active generation architecture set through SDXL, Stable Diffusion 3 Medium, and Stable Diffusion 3.5 Medium, adds component-based Advanced Models composition, makes recoverable generation queues persistent across application sessions, and continues the runtime refactor that separates large generation/catalog responsibilities without intentionally changing established behavior.

The current normal text-to-image architecture set is now:

- Stable Diffusion 1.x;
- qualified Stable Diffusion 2.x;
- Stable Diffusion XL (SDXL);
- Stable Diffusion 3 Medium; and
- Stable Diffusion 3.5 Medium.

SD3 Medium and SD3.5 Medium normal txt2img generation have been verified with generated-image tests in the current source snapshot.

## Stable Diffusion Architecture Expansion

### SDXL Is an Active Generation Architecture

The public feature documentation previously lagged behind the runtime and still described SDXL as planned or inspection-only in several places. The current source has an active SDXL generation path with architecture-specific preflight and runtime profiles.

The SDXL path includes:

- dual tokenizer and dual text-encoder handling;
- pooled prompt embeddings;
- added conditioning/time IDs;
- SDXL-specific UNet invocation;
- architecture/runtime preflight;
- base SDXL profile support; and
- profile-aware recommendation handling for specialized families such as Lightning and Turbo.

Model-profile recommendations remain advisory unless the user explicitly opts into the corresponding recommended Steps or CFG behavior. Sampler/scheduler choices are not silently rewritten merely because a profile has a preferred pair.

### Stable Diffusion 3 Medium and SD3.5 Medium

ImageGen now supports normal WebUI txt2img generation for recognized **Stable Diffusion 3 Medium** and **Stable Diffusion 3.5 Medium** checkpoints.

The SD3-family runtime introduces an architecture contract that differs materially from SD 1.x/2.x/XL:

- transformer/MMDiT-oriented denoising instead of the earlier UNet contract;
- Flow Match denoising semantics;
- 16-channel latent handling;
- architecture-specific VAE behavior;
- CLIP-L + CLIP-G conditioning;
- qualified runtime profiles for `sd3_medium` and `sd3_5_medium`;
- shared or embedded text-encoder source resolution;
- a `flow_euler` sampler path;
- a `flow_match_euler` scheduler path; and
- staged component residency so large learned components do not all need to remain GPU-resident while idle.

The normal WebUI path currently uses the qualified CLIP-L + CLIP-G mode. Optional T5/T5XXL component support exists for Advanced Models and backend qualification, but ordinary WebUI T5 selection remains a separate advanced workflow boundary.

### SD3 Support Installer

A new support helper is available after the main ImageGen environment has been installed:

```bat
install_sd3_support.bat
```

The SD3 support installer provisions the runtime configuration/tokenizer assets and shared text-encoder files required by the supported SD3 profiles. It intentionally does **not** download a user's main Stable Diffusion checkpoint.

The shared encoder library uses canonical component locations under:

```text
models\StableDiffusion\TextEncoders
```

This allows compatible checkpoints to reuse shared CLIP/T5 assets rather than requiring every checkpoint file to embed duplicate text-encoder weights.

## Advanced Models and Component Composition

ImageGen now has a user-facing **Advanced Models** mode for composing a generation model from registry-fingerprinted components.

Whole Checkpoint mode remains the normal default. Advanced Models is opt-in and changes the model-selection authority from one checkpoint filename to an explicit component composition.

Current architecture-family contracts cover:

- SD 1.x: model/UNet weights, VAE, and text encoder;
- SD 2.x: model/UNet weights, VAE, and text encoder;
- SDXL: model/UNet weights, VAE, text encoder 1, and text encoder 2; and
- SD3/SD3.5: transformer/model weights, VAE, CLIP-L, CLIP-G, and optional T5/T5XXL.

### Exact Component Identity

Advanced Models uses component fingerprints rather than filenames as the durable identity.

A selected component can be available as:

- a standalone physical component file;
- a digital component inside one or more donor checkpoints; or
- both physical and digital sources for the same exact fingerprint.

Multiple files containing the same exact component fingerprint remain one component choice. Source location and component identity are separate concepts.

### Conservative Auto Selection

Required component roles can use **Auto** only when exactly one eligible compatible component fingerprint is available.

If multiple unique compatible fingerprints exist, ImageGen requires an explicit choice instead of guessing. Optional roles remain opt-in and are not silently enabled.

### Component Registry Refresh and Relinking

The component registry can scan the configured model library and additional model-library roots, retain historical source locations, and distinguish currently reachable from unavailable sources.

When a checkpoint has been copied or moved, exact whole-file SHA-256 evidence can relink the new reachable path to already-known component identities rather than rebuilding compatibility from filenames.

Advanced Models selections are persisted into generation settings, replay records, queue/batch workflows, and output manifests using the selected component identities.

## Persistent Generation Queue

Recoverable generation queues now persist between application sessions.

ImageGen stores enough scheduler/job state to restore:

- queued jobs;
- explicit queue ordering;
- individually paused queued jobs;
- whole-queue hold state; and
- recoverable multi-image progress/seed history.

If ImageGen closes while a generation is active, the interrupted job can be restored at the front of the queue. The queue is deliberately restored in a held state instead of immediately restarting GPU work when the application opens again.

The user must explicitly Resume before recovered work proceeds.

Completed jobs, failed jobs, and ordinarily user-cancelled jobs are not requeued.

## Runtime Architecture Hardening

This update also contains several substantial internal refactors intended to make future feature work safer and easier to isolate.

### KES Scheduler Decomposition

The KES scheduler implementation has been separated into focused responsibilities for:

- schedule construction;
- sigma-cache behavior;
- randomization;
- blending;
- stabilization; and
- diagnostics.

The public scheduler behavior and existing high-sigma behavior were intentionally preserved during the refactor.

### txt2img Runtime Coordinator

The large txt2img runner has been decomposed behind the existing `Txt2ImgRunner` surface into separate services for:

- model preflight;
- pipeline construction;
- component residency/cache behavior; and
- request execution.

The goal is responsibility separation rather than a second generation engine. WebUI, replay, batch, and normal txt2img execution continue to converge on the same runtime contracts.

### Catalog and Replay Infrastructure

Catalog responsibilities are now separated by domain, while replay-related services share a common preflight-token lifecycle instead of independently implementing the same TTL/locking/token-copy behavior.

The shared preflight token store is used by:

- replay;
- batch replay;
- batch import; and
- Variation Matrix workflows.

Feature-specific validation remains owned by each workflow.

## Public Documentation Corrections

The public documentation has been brought back into alignment with the published runtime.

Updates include:

- README architecture support now names SD1.x, qualified SD2.x, SDXL, SD3 Medium, and SD3.5 Medium;
- SD3 support setup is documented;
- `features/CURRENT.md` no longer says SDXL is blocked;
- Advanced Models and queue persistence are included in the current-feature inventory;
- SDXL has been removed from the upcoming-feature list;
- SD3 workflow-expansion work is listed separately from already-supported normal txt2img; and
- the changelog folder now has an index file so the README's Changelog link resolves to a real document.

## Current Boundaries

This release remains alpha software. Architecture support does not mean that every checkpoint, adapter, or secondary workflow belonging to that family has been independently qualified.

Important current boundaries include:

- normal SD3/SD3.5 txt2img is supported, while SD3 Hires, SD3 LoRA, Img2Img, and REGION/Canvas combinations remain separate qualification areas;
- the explicitly qualified SD3 normal-generation profiles are SD3 Medium and SD3.5 Medium rather than every possible SD3-family variant;
- general Img2Img and inpainting are still planned;
- LoHa, LoKr, DoRA-specific extensions, and other non-standard adapter algorithms are not automatically executable merely because they can be detected;
- ControlNet, active Textual Inversion application, and Hypernetworks are not active generation features; and
- Advanced Models component compatibility is evidence-based, but not every possible free-form cross-checkpoint combination should be assumed empirically validated.

For the current feature inventory, see [`features/CURRENT.md`](../features/CURRENT.md). For current qualification and alpha boundaries, see [`features/LIMITATIONS.md`](../features/LIMITATIONS.md).
