# ImageGen Update — 2026-08-12

> **Status:** Alpha development snapshot
> **Application version in current source:** `0.1.0-alpha.1`

This update expands ImageGen beyond the previous SD 1.x-only public boundary and adds several user-facing systems around model compatibility, asset management, workspace organization, appearance, help, generation control, randomization, replay safety, and queue quality-of-life.

The largest runtime change is the addition of qualified **Stable Diffusion 2.x generation** using a dedicated OpenCLIP conditioning/runtime-profile path. SDXL remains blocked for base-model generation, although the LoRA compatibility layer can already identify and reason about SDXL adapter targets separately from base-model generation availability.

## New and Expanded Features

### Qualified Stable Diffusion 2.x Generation

ImageGen now has an enabled SD 2.x generation capability for checkpoints that satisfy the SD 2.x runtime contract.

The SD 2.x path includes:

- checkpoint architecture inspection and qualification;
- explicit SD 2.x runtime profiles;
- local OpenCLIP tokenizer/text-encoder conditioning;
- 1024-wide text-conditioning validation;
- checkpoint-derived SD 2.x text-encoder conversion/loading;
- prediction-type resolution for epsilon and v-prediction-oriented profiles;
- runtime asset resolution for SD 2.x UNet, VAE, and text-encoder configuration;
- explicit profile overrides when model metadata is not sufficient; and
- normal generation capability gating through the same architecture contract used by the rest of ImageGen.

Known runtime-profile definitions now cover the major SD 2.0/2.1 base and 768-oriented profile families. Individual checkpoints still need to satisfy ImageGen's qualification requirements; the existence of an SD 2.x label alone is not treated as proof that a checkpoint is safe to run.

SDXL remains intentionally blocked for base-model generation until the dual-tokenizer/dual-text-encoder, pooled-conditioning, time-ID, and SDXL-specific UNet-call contracts are implemented and qualified.

### Standard LoRA Compatibility Layer

The LoRA runtime has been reorganized around explicit adapter inspection, compatibility, loader registration, and target mapping rather than treating every Safetensors adapter as one undifferentiated LoRA file.

The current standard loader recognizes conventional representations including:

- Kohya-style standard LoRA;
- Diffusers/PEFT LoRA; and
- conventional `lora_up` / `lora_down` representations.

Compatibility reporting now separates:

- detected Stable Diffusion family;
- adapter format;
- expected target components;
- loader/runtime support; and
- technical file evidence versus provider/sidecar metadata.

Standard linear and supported convolutional LoRA targets can be mapped through the registered standard loader when the component mapping is complete.

Current target awareness includes:

- SD 1.x UNet and text encoder 1;
- SD 2.x UNet and text encoder 1; and
- SDXL UNet, text encoder 1, and text encoder 2 target identification for adapter compatibility work.

SDXL adapter-target readiness does **not** enable SDXL image generation by itself.

ImageGen can also identify adapter families such as LoHa and LoKr without pretending the standard loader can execute them. Unsupported or partially supported formats are blocked explicitly instead of silently dropping unknown tensor groups. DoRA-specific magnitude data is likewise treated as an extension that requires its own qualified runtime path.

### Asset Hub

ImageGen now includes a provider-neutral **Asset Hub** foundation for discovering, downloading, verifying, classifying, installing, and tracking model-related assets. Civitai is the first supported provider.

The current lifecycle is:

```text
provider discovery
-> secure download plan
-> temporary staging
-> size/SHA-256 verification
-> install plan
-> technical classification
-> atomic installation or quarantine
-> provenance sidecar/index update
```

Important behavior includes:

- provider credentials remain backend-owned rather than being returned to the browser;
- Civitai credentials are not forwarded to unexpected redirect hosts;
- downloads are staged outside live model folders;
- queued downloads support cancellation and safe resume where possible;
- completed downloads are not marked `In Library` until installation succeeds;
- files are reclassified using ImageGen's own technical inspectors instead of trusting provider labels alone;
- unsupported or ambiguous files can be quarantined rather than guessed into a model folder;
- final installation uses configured project asset roots;
- staged and copied files are SHA-256 verified;
- final commits use an atomic destination-side replace/rename path; and
- installed assets retain portable `.imagegen.json` provenance plus a derived local searchable index.

Current classification paths cover checkpoints, LoRAs, neural upscalers, recognizable VAE files, and safely readable textual-inversion Safetensors payloads. Asset Hub installation support does not automatically make every asset type an active generation feature.

### Upscaler Favorites and Asset-Aware Hires Recovery

Upscaler selection now has stronger persistent preference and compatibility behavior.

ImageGen can retain favorite/preferred upscaler identities, distinguish compatible favorites from unavailable entries, and preserve the user's preferred Hires upscaler instead of letting unrelated replay state silently replace it.

When Hires is enabled without a usable upscaler, the UI now directs attention to the affected Hires control and provides recovery guidance instead of relying only on a detached error message. Recovery can point users toward asset refresh/install actions or configured asset paths.

### Help Center and Shared Markdown Viewing

A user-facing **Help Center** is now part of the WebUI.

The Help Center provides:

- public documentation from the separate `help_documentation/` tree;
- topic/category navigation;
- search suggestions after a useful minimum query length;
- related-topic navigation;
- shared Markdown rendering;
- repository-owned image/video support; and
- explicit external HTTPS links rather than silently embedding third-party remote content.

The Home Changelog component now uses the same shared Markdown capability instead of maintaining a separate Markdown parser/viewer. It can still fall back to changelog files bundled with the installed build when the public repository is unavailable.

### Theme Manager

Theme Manager now uses semantic appearance roles rather than limiting customization to a few ad hoc colors.

Current semantic roles include:

- accent;
- primary surface;
- secondary surface;
- component/card surface;
- component border;
- component accent;
- primary text; and
- secondary/muted text.

The editor includes live contrast diagnostics. A 4.5:1 ratio is treated as a recommended text-readability target rather than a forced color rewrite. Low-contrast themes remain allowed, but ImageGen warns before Save/Apply by default; that confirmation preference can be disabled while diagnostics remain visible.

Theme Manager also supports local ZIP-compatible theme packages with validation, explicit activation, package-library storage, and safe fallback when an active package becomes unavailable or corrupt.

Theme packages are treated as visual data rather than executable extensions. Executable/script content, unsafe paths, symbolic-link abuse, and unsafe SVG content are rejected. Optional scoped CSS requires an explicit package capability.

### Workspace Manager and Responsive Component Layouts

ImageGen now has a **Workspace Manager** built around registered workspace components.

Components can declare:

- stable identity;
- supported pages;
- presentation variants;
- size constraints; and
- shared capabilities they depend on.

Workspace layouts are saved as portable base layouts. Wide, Standard, Compact, and Narrow presentations derive from the same saved structure based on actual workspace-container width instead of requiring four unrelated layouts.

This component architecture is also used by newer shared features such as Help Center and Changelog Markdown presentation.

## Generation Quality-of-Life Improvements

### Reactive Seed Strategy and Advanced Seed Ranges

Seed handling now supports a dedicated advanced strategy UI directly beneath the normal Seed field.

Normal fixed/random seed behavior remains simple, while advanced mode exposes:

- sequential progression;
- unrestricted random seeds;
- random seeds within a selected range; and
- optional duplicate avoidance until a finite selected range is exhausted.

The Seed expression and structured strategy controls are synchronized.

Accepted range forms include:

```text
[5000,15000]
-1 [5000,15000]
-1, [5000,15000]
```

The punctuation after `-1` is optional. Structured controls and freeform expressions normalize to the same seed plan instead of maintaining separate interpretations.

Finite random ranges preserve their consumed-seed state across pause/resume boundaries so resuming a batch does not restart the uniqueness cycle.

### Advanced Numeric Randomization and Hard Bounds

Numeric generation fields can now use reusable advanced range specifications.

A range can randomize a numeric value per generated image while independent hard minimum/maximum locks constrain the resolved value. Integer-only resolution is available where appropriate.

The advanced-range editor is field-aware rather than inheriting Seed examples. For example, CFG Scale uses CFG-appropriate examples such as:

```text
[5.0, 7.5]
```

The expression and structured min/max fields synchronize in both directions, and valid structured controls are authoritative on Apply rather than being rejected solely because a freeform expression used optional punctuation differently.

### CFG Lab Presets and Runtime Locks

CFG Lab now supports persistent user presets in addition to built-in presets.

Current preset workflows include:

- save current CFG Lab state;
- update/replace saved state;
- import/export preset files; and
- preserve associated CFG-related random-range settings.

CFG effective minimum/maximum locks are enforced by the guidance runtime, allowing per-step CFG trajectories to be clamped to the user's selected bounds.

### Queue Pause, Resume, and Reordering

The generation queue now has item-aware pause/resume behavior instead of treating pause only as a single global queue state.

Current behavior includes:

- pausing queued items so the scheduler can skip them;
- pausing active multi-image work at a safe image boundary;
- retaining progress for resumed work;
- resuming held queued jobs back into schedulable order;
- showing paused job state distinctly in the queue;
- displaying finite and continuous-generation progress; and
- moving queued jobs higher or lower without silently replacing the currently active generation.

Seed-range consumption and generation progress are preserved across pause/resume boundaries.

### Variation Matrix Queue Flow

Variation Matrix no longer requires users to understand a separate `validated job` object before queueing a previewed expansion.

Validation still exists internally, but preview/queue behavior can transparently validate or revalidate the current plan and queue the expanded jobs when valid. A preview representing five Cartesian jobs can therefore be submitted as five jobs without a redundant manual validation ceremony.

### Replay Preference Boundaries

Replay now distinguishes generation/reproducibility state from user-owned operational preferences more carefully.

Historical runs no longer silently force current preferences such as:

- TXT sidecar creation;
- compact JSON sidecar preference;
- diagnostics JSON preference;
- saving the exact low-resolution Hires base artifact; or
- the user's preferred Hires upscaler when the replay does not require one.

Legacy replay records that contain older artifact flags are normalized toward current safe defaults instead of automatically re-enabling historical output choices.

### Output Defaults

Current output defaults now favor the compact replay path:

- TXT sidecar: **off by default**;
- compact replay JSON: **on by default**;
- diagnostics JSON: **off by default**; and
- exact low-resolution Hires base artifact: **off by default**.

These remain user-configurable operational choices rather than exact-replay requirements.

### User Configuration Editor

The WebUI now includes an in-program editor for `user_config/user-config.yml`.

The editor validates YAML before saving, writes atomically, and keeps a `.bak` copy of the previous configuration so invalid or interrupted edits are less likely to destroy the active configuration file.

### REGION Placement and Overlap Selection

REGION editing has additional quality-of-life behavior for crowded canvases.

New region boxes prefer nearby empty/low-overlap space instead of blindly stacking on top of existing boxes when a reasonable free placement exists.

When multiple regions overlap or contain one another, a region-stack selector can expose the regions at that location so a buried box can be selected directly.

## Runtime and Architecture Work

### Model-Qualification and Reference Contracts

The model-loading stack now has stronger explicit qualification/reference components for SD 2.x, including runtime-profile resolution, retained reference configurations, checkpoint fingerprint qualification, component comparison, and OpenCLIP reference conversion.

These contracts reduce the need to guess architecture or prediction behavior from a filename alone.

### Attention and Guidance Integration

The current changes continue to route attention backend selection and effective CFG/guidance through explicit runtime contracts. This is important for SD 2.x support and for the newer hard CFG range-lock behavior because generation-time controls remain part of the normal runtime rather than being implemented as UI-only metadata.

## Public Documentation

A new public `help_documentation/` tree now carries user-facing Help Center material independently from the private/internal `docs/` engineering workspace.

Current public help includes material for:

- Asset Hub authentication, downloads, verification, installation, conflicts/quarantine, provenance, upscaler preferences, and troubleshooting;
- Help Center media/link behavior;
- LoRA runtime compatibility;
- standard LoRA support across SD 1.x, SD 2.x, and SDXL target inspection;
- Theme Manager colors, contrast, and local packages;
- Workspace Manager and responsive layouts; and
- Home Changelog/Help Center behavior.

## Current Compatibility Boundary

The current public generation boundary is now:

- **SD 1.x:** enabled;
- **qualified SD 2.x:** enabled;
- **SDXL:** not yet enabled for base-model generation.

The standard LoRA runtime covers qualified conventional LoRA representations. LoHa, LoKr, DoRA-specific extensions, and other non-standard algorithms may be detected and described but should remain blocked unless a dedicated qualified loader exists.

General Img2Img, inpainting, ControlNet generation, and Hypernetwork generation are still outside the current public runtime.
