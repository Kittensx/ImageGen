# ImageGen Update — 2026-08-08

> **Status:** Alpha development snapshot  
> **Application version in current source:** `0.1.0-alpha.1`

This update summarizes the current user-visible state beyond the original monolithic README. It reflects the current runtime direction: SD 1.x txt2img remains the supported model-family foundation, while LoRA, neural Hires, Canvas Expansion, replay/output storage, and runtime lifecycle work have advanced substantially.

## New and Expanded Features

### Canvas Expansion / Shape Adaptation

ImageGen now has a generative canvas-expansion workflow for producing a larger composition without stretching the protected source image.

Current entry points include:

- **Expand Existing Image** — load an existing image and generate the newly exposed canvas around the protected source.
- **Expand After Generation** — expand a fresh txt2img result inside the same generation flow before the expanded result becomes the primary output.

Current expansion behavior includes:

- explicit target dimensions;
- square/custom target shapes;
- source placement/anchor controls;
- preserve, feather, and generate regions;
- Edge Pad context seeding;
- Reflect Pad as an advanced alternative;
- expansion denoising controls;
- dedicated extension positive/negative prompts;
- source-versus-extension prompt policy;
- image re-encode/live latent/automatic source-handoff modes;
- latent alignment/fallback reporting;
- replayable expansion configuration; and
- geometry/inference fingerprints for diagnostics.

Canvas Expansion is intentionally positioned as an **intermediate image workflow**. It is designed to prepare a useful expanded composition for future Img2Img refinement rather than pretending to replace a complete Img2Img system.

### LoRA Runtime and Workspace

LoRA is now part of the active generation system.

Current LoRA behavior includes:

- discovery and compatibility scanning;
- weighted application;
- multiple LoRAs per generation;
- structured LoRA records and inline syntax normalization;
- SHA-256-backed identity/provenance;
- checkpoint-family compatibility checks;
- activation/sidecar metadata;
- generation/replay recording; and
- dedicated LoRA WebUI browsing/selection.

The current WebUI also includes CivitAI-oriented LoRA metadata and preview workflows.

### Pixel-Neural Hires

Hires is now built around supported neural `.pth` upscalers rather than the earlier latent-only interpolation path.

The current flow is:

```text
base denoise
-> VAE decode
-> neural .pth upscale
-> exact target-size preparation
-> VAE encode
-> second denoise/refinement
-> final VAE decode
```

The current Hires system includes upscaler discovery/qualification, tiling controls, exact target sizing, replay identity, stage-aware memory handling, and bounded recovery for eligible out-of-memory cases.

## Performance and Runtime Improvements

Recent runtime work reduces unnecessary component residency and stage overlap, especially in multi-stage Hires generation.

The generation/runtime path now has clearer stage ownership across base denoising, VAE decode, neural upscaling, VAE encode, second-pass denoising, and final decode. This allows inactive components to be released or offloaded more deliberately under the selected memory policy.

Current alpha testing has also shown substantially faster normal txt2img and Hires completion than earlier development builds on the currently tested hardware. These observations are not universal benchmarks; performance still depends on hardware, model, target size, sampler/scheduler, attention backend, preview configuration, and memory pressure.

## Replay and Output Storage Improvements

The normal JSON sidecar is now a **compact authoritative replay record** rather than an unfiltered copy of the complete execution state.

The compact replay serialization removes or prunes redundant structures such as:

- duplicate prompt-asset records;
- non-generation scheduler fields;
- duplicate schedule/config copies;
- unnecessary full runtime-conformance snapshots; and
- empty records.

Deeper execution information is kept in a separately pruned diagnostics representation when diagnostics are saved.

This separation reduces metadata redundancy, keeps replay records easier to inspect, and lowers save/finalization storage overhead.

### Atomic Output Saving

The current save path writes image and sidecar data to temporary paths before committing final filenames. If the transaction fails, temporary/partially owned files are cleaned up rather than intentionally leaving a partially committed generation batch.

## Prompt and UI Improvements

The current source includes the newer **SuperHybrid** prompt path alongside the existing parser system, prompt shortcuts/presets, prompt validation, regional prompt tooling, and expanded prompt-authoring controls.

The WebUI has also moved toward more focused workspaces, particularly for checkpoint and LoRA management, while Generation remains the primary production surface.

## Replay and Advanced-Workflow Provenance

Replay/output records now carry more of the information required to understand advanced workflows such as LoRA stacks, neural Hires, and Canvas Expansion.

For Canvas Expansion this includes source/target geometry, placement, prompt overlays, preservation behavior, context seed, source handoff, latent alignment, and deterministic metadata fingerprints.

For Hires this includes neural upscaler identity, target sizing, second-pass settings, relevant VAE/upscaler provenance, and advanced-stage behavior required for replay validation.

## Current Compatibility Boundary

The current generation family remains **SD 1.x only**.

SD 2.x and SDXL are planned but intentionally blocked until their different conditioning/model contracts are implemented.

General Img2Img and inpainting are also not yet part of the public runtime. Canvas Expansion can use an existing image as a protected source, but it should not be confused with a general image-conditioned redraw/refinement module.

## Installation Direction

The public setup path is now centered on the profile-driven Windows installer.

The current installer requires **Python 3.10.20 x64 exactly**, scans the NVIDIA GPU/driver, matches a validated hardware profile, creates the project `.venv`, installs the qualified PyTorch/custom-attention/requirements stack, writes runtime configuration, and validates the result.

The current published hardware manifest contains a validated NVIDIA Blackwell SM120 profile and does not allow silent use of unvalidated hardware/package combinations.
